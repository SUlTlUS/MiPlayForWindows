# Android MiPlay 投送协议完整移植计划

更新日期：2026-09-03

## 目标与开发约定

以本仓库 Windows 端实际使用的 MiPlay 投送链路为基准，完整移植到 Android。目标包括单音箱、多音箱同步、运行中加入和退出音箱、播放控制及异常恢复，不以“能连上”或“能同时向两个 Socket 写数据”作为完成标准。

开发阶段按以下约定推进：

- 可以直接重构 Android 协议层、修改内部接口和数据结构，不保留旧实现的兼容分支。
- 可以直接用现有 Root 手机和音箱测试，包括停止旧投送、覆盖安装、重启 SystemUI、重复连接和切换音箱，不再为这些常规开发操作逐项等待确认。
- 不把特定网络条件、额外音箱、完整测试设备或旧版本兼容性作为开工前提。有现成设备就直接测试，暂时覆盖不到的场景明确记录。
- 不截图；不把已经删除的测试音功能加回正式应用。编码与协议测试可以使用临时测试数据。
- 测试和实现并行推进，不用构建成功、编码帧率正常或收到 `state=2` 代替实际播放结果。
- 本文是后续实施计划；未完成项不能因为文档已写入而标记为完成。

## 移植范围

### 主线：Windows 已接入的播放协议

从设备发现到关闭会话，覆盖完整链路：

1. MiPlay mDNS 发现、设备身份和地址更新。
2. Legacy 8899 控制连接、安全挑战、版本与设备信息、播放源、Open/Close。
3. 反向 RTSP、辅助连接、音频连接、WFD 参数协商、UDP 时钟同步。
4. PCM 分帧、AAC 编码调度、ADTS/MPEG-TS/RTP/TCP 封装。
5. 共享媒体时钟、组级 TIME_OFFSET、发送同步和运行期时间修正。
6. 多音箱成员管理、历史帧补发、动态加入与退出。
7. 暂停、继续、音量、媒体信息、状态通知、心跳与命令确认。
8. 采集停顿、编码阻塞、网络中断、取消与资源释放。

仅替换必须依赖操作系统的部分：Windows WASAPI 对应 Android Root 内录；Media Foundation/FFmpeg 编码器对应 Android MediaCodec；Windows 计时和网络接口对应 Android 实现。采样参数、协议字节和状态转换不能因平台不同而随意简化。

### 其他协议代码

Windows 仓库还包含现代 SafetyAuth/S12、Continuity、IDM 等算法和取证代码。清点时必须分别标注“已用于播放”“独立算法”“仅研究/探针”，同步移植需要的算法与测试；不能将尚未构成播放链路的探针描述为已实现的投送功能，也不能拿它们替换主线的可运行实现。

本轮不重做界面，不移植 Windows 专用驱动、WASAPI API 或仅供取证的桌面工具。应用内界面和 SystemUI 都应接入同一个 Android 协议核心。

## 当前状态与差距

### 已接入的基础

- MiPlay 发现、8899 基础握手、反向 RTSP 与音频连接。
- AAC-LC、48 kHz、双声道、256 kbps，以及基础 ADTS/MPEG-TS/RTP 封装。
- 从 Windows 移植的 1024 采样分帧、独立编码输入/输出、12 帧有序缓冲、14 帧启动预缓冲。
- Root 内录改为小块读取，避免每次积攒约 250 ms 音频再挤入较小队列。
- 组内共用 PCM 取帧结果，同声道共用编码结果。
- 应用和 SystemUI 的基础控制入口、设置页及状态桥接。

已有的 58 项单元测试和真机单双路编码检查，只覆盖对应基础功能；不代表多音箱投送协议已经完整移植。

### 尚未对齐的核心行为

| 项目 | Android 现状 | 需要达到的 Windows 行为 |
| --- | --- | --- |
| 动态加入 | `MiPlaySharedMediaBroadcaster` 保留 47 个 AU；新订阅先取历史，再接收后续共享帧 | 仍需真机验证 A 播放中加入 B 的连续听感和边界 |
| 组时钟 | 初始成员使用共同屏障；`MiPlaySharedTimeOffsetState` 保存已提交值，晚加入复用该值 | 运行期 Resume/停顿恢复的更新尚未接入 RTSP |
| 发送同步 | 每个接收端有独立队列、发送协程和 Packetizer；每个实时 AU 由共享完成协调器收齐后推进 | 仍需真机验证阻塞/恢复时的同步偏差 |
| 封包状态 | `MiPlayMediaPacketizerSnapshot` 保存 RTP 序号、TS 连续计数和 AU 索引，晚加入从历史起点恢复 | 仍需完整对照 Windows 的 PTS/PCR 修正与回绕 |
| 输出时间线 | `MiPlaySharedOutputTimeline` 已统一生成共享 PTS/PCR，并在每帧发送完成后提交一次停顿补偿 | 运行期 TIME_OFFSET 提交和真机停顿恢复仍待验证 |
| 控制确认 | 运行期读取独立于写入；音量 ACK 精确匹配命令、序号和载荷，心跳有看门狗；暂停/继续仍只区分“请求已发出”和通知确认 | 继续补齐所有控制命令的 Windows ACK/超时策略 |
| 成员与资源 | 共享采集/AAC 资源，动态成员上限按协议组 63 台；成员订阅退出不销毁公共资源 | 软件上限不等于真机已验证数量 |
| 失败状态 | 控制、媒体发送和队列错误可回到会话 `failureMessage`，订阅关闭会清理发送任务 | 还需区分单成员失败与公共音源失败的影响范围 |

### 本轮进度（2026-09-03）

- 已完成运行期控制的独立读循环、串行写入、音量 ACK 精确匹配、心跳响应与 15 秒无活动检测。
- 已完成组级 `TIME_OFFSET` 保存和晚加入复用，旧的运行期提交不能覆盖更新的组值。
- 已完成 47 个 AU 历史窗口、共享 AU 编号、晚加入队列和各接收端独立发送任务；Packetizer 支持状态快照恢复。
- 已完成共享输出时间线的 PTS/PCR 生成、状态缓存和每帧发送完成后的停顿补偿入口。
- 已增加对应的 JVM 回归测试；这些测试证明字节/队列/状态边界，不证明真实音箱已经出声。
- 仍未标记为完成：RTSP 运行期 `TIME_OFFSET`、控制失败后的成员隔离、真实设备动态加入/退出和停顿恢复听音验证。

关键 Android 文件在 `android/app/src/main/java/com/suitius/dlnacast/miplay/`，主要是 `MiPlayCastSession.kt`、`MiPlayControl.kt`、`MiPlayRtsp.kt` 和 `MiPlayMediaPacketizer.kt`。

## 实施顺序

### 第一阶段：建立完整对照清单与协议核心边界

- [ ] 沿 Windows 实际入口梳理调用链，列出全部参与播放的类、状态机、常量、消息与测试。
- [ ] 给每项标注 Android 对应实现、差异和移植状态，避免仅按文件名复制而漏掉调用路径。
- [x] 把设备连接、组会话、时钟、媒体队列、控制通道拆开；界面和服务不再直接维护协议细节。
- [ ] 保留统一的 Android 采集、编码、单调时钟和 Socket 适配接口。

Windows 依据：`MiPlaySystemAudioTransmitter`、`MiPlayLegacySystemAudioSessionRunner`、`MiPlaySharedAudioSession`。

完成标准：能够明确回答“一个操作经过哪些协议状态、拥有哪些资源、由谁提交最终结果”。

### 第二阶段：完整移植控制通道与 RTSP 状态机

- [ ] 对齐握手次序、命令序列号、设备信息与播放源载荷。
- [x] 移植运行期控制通道：串行写入、独立读取、精确 ACK 匹配、心跳监控和失败传播。
- [ ] 对齐暂停/继续的重复发送与等待策略，区分“请求已发出”和“接收端状态已确认”。
- [ ] 完整处理 RTSP 分包、合包、请求与响应关联、运行期 TIME_OFFSET 更新及关闭流程。
- [ ] 对齐 UDP 时钟包、延迟回报和时间偏移的计算单位。
- [ ] 清理仅用于模拟已抓取设备的硬编码元数据，实际传入当前会话信息。

Windows 依据：`MiPlayLegacyAudioSourceSession`、`MiPlayLegacyPlaybackControlSession`、`MiPlaySharedRuntimeControlChannel`、`MiPlayLegacyRuntimeControlSequence`、`MiPlayWfdSourceRtspSession`、`MiPlayWfdTimerResponder`。

完成标准：同样的输入消息在两端产生同样的状态转换和输出消息；超时和断开不会被当作成功。

### 第三阶段：移植共享媒体时钟与封包状态

- [x] 移植 `MiPlaySharedOutputTimeline`，使用全局 AU 编号和统一输出时间线。
- [ ] 移植 `MiPlaySharedTimeOffsetState`，保留初始化、运行期准备与提交规则，防止迟到的旧更新覆盖新值。
- [ ] 对齐 PCR 基值及扩展位、PTS/RTP 时间戳、回绕、PAT/PMT 周期和 TS 连续计数。
- [x] 移植 Packetizer 状态快照与时间线推进，不把“共用 AAC 数据”误当作“所有接收端永远共用一个封包器”。
- [ ] 对齐 Windows 发送停顿补偿，避免各音箱自行修正时钟而产生漂移。

Windows 依据：`MiPlaySharedOutputTimeline`、`MiPlaySharedTimeOffsetState`、`MiPlayWfdMediaClock`、`MiPlayWfdAudioPacketizer`、`MiPlayMpegTsAudioMuxer`、`MiPlayMediaStallRecoveryPlan`。

完成标准：固定输入和时间源下，比较完整媒体序列，而不只比较首包；所有组成员共享同一逻辑媒体时间。

### 第四阶段：完整移植多音箱会话

- [x] 移植带全局 AU 编号的发布/订阅队列和历史缓存。
- [x] 为各接收端建立独立发送任务，并加入共享发送完成协调机制。
- [x] 移植初始成员启动协调，包括共享启动预缓冲、TIME_OFFSET 和首帧边界。
- [x] 移植动态加入：按 Windows 当前实现保留并补发 47 个 AU 的历史窗口，再在明确的未来帧边界接入实时流。
- [x] 历史补发阶段不参与现有成员的实时发送屏障，不能拖停已在播放的音箱。
- [x] 新成员使用组内当前 TIME_OFFSET，不重新以自己的连接时间建立组时钟。
- [x] 移植成员退出与取消注册：移除等待者、清理独立连接，保留其他音箱使用的采集器、编码器和公共队列。
- [ ] 接入同声道共用编码、不同声道路由分开编码的完整生命周期。
- [x] 取消 Android 协议层固定两台的写死限制，沿用 Windows 核心的成员约束；软件允许的数量不直接宣称为真机已验证数量。

Windows 依据：`MiPlaySharedAudioSession`、`MiPlaySharedAccessUnitBroadcast`、`MiPlaySharedStartupAccessUnitBuffer`、`MiPlaySharedSendCompletionCoordinator`、`MiPlaySharedMediaCoordinator`、`MiPlaySharedRouteEncoder`。

优先验证：A 正在播放时加入 B，移除 A 后 B 继续播放，再重新加入 A。不能通过重启整组来掩盖动态加入逻辑缺失。

### 第五阶段：组级控制、恢复和生命周期

- [ ] 移植组级暂停/继续，协调采集、编码输入、媒体发送和接收端命令，避免只改变一个布尔状态。
- [ ] 移植继续播放和网络停顿后的组级 TIME_OFFSET 更新。
- [ ] 对齐总音量、单音箱音量及 ACK 回报；控制目标使用稳定设备身份，不依赖易变化的列表位置。
- [ ] 移植采集不连续、编码队列阻塞及传输停顿的恢复规则。
- [ ] 区分单成员主动退出、成员连接失败与公共音源失败，按 Windows 行为决定影响范围。
- [ ] 检查关闭、取消、重复开始、开始中停止以及成员变化时的资源释放和等待解除。
- [ ] 重连与重试遵循 Windows 已实现的策略，不额外加入无限重试或无依据的“自动修复”。

Windows 依据：`MiPlaySharedPlaybackControlCoordinator`、`MiPlayCaptureDiscontinuityRecovery`、`MiPlayMediaStallRecoveryPlan`、`MiPlaySharedTimeOffsetState` 及会话关闭流程。

完成标准：状态、实际连接和拥有的资源一致，不出现控制显示成功但消息未确认、成员已退出但仍阻塞其他成员等情况。

### 第六阶段：统一应用和 SystemUI 入口

- [ ] 应用和 SystemUI 调用相同的组会话 API，不各自维护一套音箱选择逻辑。
- [ ] 投送选择、连接中、已连接、暂停、失败均由协议核心状态派生。
- [ ] 只在目标音箱初始化期间显示加载动画，扫描不冒充连接。
- [ ] 单音箱使用总音量，多音箱按成员提供音量控制；音量值跟随实际设备回报。
- [ ] 设置页参数完整进入新建组会话；向现有组加入设备时遵循该组当前参数。
- [ ] 清理旧的临时实现及文档中不再符合 Root 投送路径的说明。

本阶段以接通协议状态为主，不重新设计已经确认过的界面样式。

## 验证方式

不等“测试条件全部准备好”再开发。每完成一块，就用当前能运行的方式验证并记录结果：

- **跨端对照**：把 Windows 已有消息、时间戳、封包、ACK 和多成员测试转换为 Android 测试。优先覆盖晚加入补发、帧边界切换、TIME_OFFSET 提交及取消注册。
- **本地回归**：检查连续 AU 编号、字节内容、队列顺序、时间戳回绕和关闭时线程退出。
- **真机自动测试**：直接安装、重启相关作用域并执行单/多音箱控制；收集帧率、丢帧、发送间隔、同步偏差、ACK 与失败状态，不仅看构建结果。
- **播放验证**：用正在使用的真实音频检查声音连续性、单音箱和多音箱听感。若没有可用听音证据，应写“待听音确认”，不能凭编码数据推断声音正常。

现有设备优先执行以下序列：

1. 单音箱开始、暂停、继续、改音量、停止。
2. 同时启动两台音箱，分别控制音量。
3. A 播放中加入 B，B 完成历史补发后进入实时流。
4. 移除 A、保留 B；再加入 A；交换操作顺序。
5. 暂停期间加入/移除设备，随后整组继续。
6. 连接过程中取消，连续开始/停止，重复点选同一设备。
7. 单音箱断开、公共音源停顿、网络恢复及应用/SystemUI 重载。

更多成员可通过模拟接收端覆盖核心逻辑，不把额外实物设备作为继续开发的阻塞项。模拟结果与实物结果分别记录。

## 完成标准

- Windows 已接入投送链路中的每个协议模块都有 Android 对应项，差异仅限必要的平台接口。
- 动态加入、历史补发、共享时钟、发送协调和成员退出不再使用 Android 临时简化逻辑。
- 控制成功有对应的协议结果，所有失败能回到明确的会话状态。
- 应用和 SystemUI 展示同一份组会话状态，单/多音箱操作走同一个实现。
- 交付记录分别列出已移植、已测试、实物已验证和仍有问题的项目，不能笼统标记“全部完成”。
